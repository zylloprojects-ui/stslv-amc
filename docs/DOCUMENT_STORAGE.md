# Document Storage (Cloudflare R2)

Added 2026-11-04 on branch `feature/r2-document-storage`. Not yet deployed.

## Why

A new AMC contract must carry its contract document. Production runs on Render, whose disk is
not permanent, so `ATTACHMENTS_DIR` was deliberately left unset there and the API reported
"no file storage configured". Contracts could therefore not be added in production.

This change lets the API keep documents in a **private Cloudflare R2 bucket**. Nothing about the
contract-document requirement, the file checks or the database changes.

## How it works

```
Browser ──(signed-in request)──> API (Render) ──(S3 API, secret key)──> private R2 bucket
                                   │
                                   └── PostgreSQL (Neon): attachments row = metadata + storage_key + sha256
```

- The browser never talks to R2. Every upload and download goes through the API, which checks the
  user's permission first. No public bucket, no public URL, no presigned link.
- The R2 keys live only in Render's environment. The web app has no storage settings at all.
- Objects are stored as `attachments/<uuid>.<ext>`. The database keeps `<uuid>.<ext>` in
  `attachments.storage_key`, exactly as before. Keys are generated by the API and checked against
  a fixed pattern before every read or write, so a key can never point elsewhere in the bucket.
- Every download is checked against the SHA-256 recorded at upload (unchanged).
- Contract creation: the file is checked (type by content, size), then written to R2, then the
  contract and its document row are saved in one transaction. If the transaction fails, the
  object is deleted again. If R2 cannot be written, no contract is created (HTTP 503,
  `STORAGE_ERROR`, plain message; the R2 error is only logged by name on the server).
- An unreachable R2 is reported as `STORAGE_ERROR` (503), not as a missing file (404).

All document workflows use the same store: AMC contract documents and attachments, visit service
reports (Service Status), Service Sales report downloads, procurement and expense attachments.

## Choosing the store (API environment)

| Variables set | Store |
|---|---|
| `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (all four) | Private R2 bucket |
| `ATTACHMENTS_DIR` | Local folder |
| neither, development | `stslv-api/storage/attachments` (unchanged) |
| neither, production | none: uploads and new contracts refused (unchanged) |

Only some R2 values, or R2 together with `ATTACHMENTS_DIR`, stop the API from starting, with a
message naming the missing variable (never a value). `R2_ENDPOINT` is optional: only for a bucket
created in a jurisdiction such as the EU (`https://<account id>.eu.r2.cloudflarestorage.com`).

Check a configuration end to end (writes, reads and deletes one probe file; prints no secret):

```
npm run storage:check
```

The Security page shows "Document storage: Cloudflare R2 (private)" when R2 is in use.

## Cloudflare R2 setup (done by the owner in the Cloudflare dashboard)

1. Cloudflare dashboard → **R2 Object Storage**. If R2 is not yet enabled, enable it (Cloudflare
   asks for a payment method even for the free allowance: 10 GB storage, 1 million writes and
   10 million reads per month).
2. **Create bucket**
   - Name: `stslv-amc-documents` (any lowercase name; it becomes `R2_BUCKET`).
   - Location: *Automatic*, or the location hint *Western Europe* (the API runs in Frankfurt).
   - Jurisdiction: leave the default. (If you choose EU, also set `R2_ENDPOINT` as above.)
   - Storage class: Standard.
3. Open the bucket → **Settings**:
   - *Public Development URL*: leave **Disabled**.
   - *Custom Domains*: add **none**.
   - *CORS policy*: add **none** (the browser never contacts R2).
4. Back on the R2 overview → **Manage API tokens** → **Create API token** (an Account API token):
   - Name: `stslv-amc-api-render`.
   - Permissions: **Object Read & Write**.
   - Specify bucket(s): **Apply to specific buckets only** → `stslv-amc-documents`.
   - TTL: your choice (if you set an expiry, put a reminder to rotate it before it ends).
   - Client IP filtering: leave empty (Render's outgoing addresses are not fixed).
   - Create. Cloudflare shows the **Access Key ID** and **Secret Access Key once**. Copy them
     straight into Render (next section); do not paste them into chat, email, or any file.
5. Your **Account ID** is shown on the R2 overview page (and in the S3 endpoint
   `https://<account id>.r2.cloudflarestorage.com`).
6. Optional: bucket → Settings → *Object lifecycle rules*: none needed. Do not add a rule that
   deletes objects; old document versions are kept on purpose.

## Render environment variables (service `stslv-amc-api` → Environment)

| Key | Value |
|---|---|
| `R2_ACCOUNT_ID` | the 32-character Account ID |
| `R2_BUCKET` | `stslv-amc-documents` |
| `R2_ACCESS_KEY_ID` | the token's Access Key ID |
| `R2_SECRET_ACCESS_KEY` | the token's Secret Access Key |

Do **not** set `ATTACHMENTS_DIR` on Render. `ATTACHMENT_MAX_MB` stays at its default of 12.

The variables can be added before the code is deployed: the API now running ignores them.
Saving environment variables in Render normally restarts the service on the current commit.

## Rotating or revoking the key

Create a new token (step 4), replace `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` in Render, let
the service restart, check that a contract document opens, then delete the old token in Cloudflare.

## Existing files

- Production never stored files (storage was off), so there is nothing to move. Confirm before
  deploying with a read-only `SELECT count(*) FROM attachments;` on Neon: it should be 0.
- Local development keeps using `stslv-api/storage/attachments`. Local files are not copied to R2.
