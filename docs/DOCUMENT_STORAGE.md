# Document Storage (Supabase Storage)

Branch `feature/r2-document-storage`, 2026-11-04. Not yet deployed.

## Why

A new AMC contract must carry its contract document. Production runs on Render, whose disk is
not permanent, so `ATTACHMENTS_DIR` was deliberately left unset there and the API reported
"no file storage configured". Contracts could therefore not be added in production.

The API can now keep documents in a **private bucket** reached through an S3-compatible API.
Production uses **Supabase Storage** (Free plan, no payment details needed). Cloudflare R2 is
also supported by the same code. The contract-document requirement, the file checks and the
database are unchanged. Neon stays the database; Supabase is used only for files.

## How it works

```
Browser ──(signed-in request)──> API (Render) ──(S3 API, SigV4, secret key)──> private Supabase bucket
                                   │
                                   └── PostgreSQL (Neon): attachments row = metadata + storage_key + sha256
```

- The browser never talks to Supabase. Every upload and download goes through the API, which
  checks the user's permission first. No public bucket, no public URL, no signed link.
- The S3 keys live only in Render's environment. The web app has no storage settings at all.
- Objects are stored as `attachments/<uuid>.<ext>` in the bucket. The database keeps
  `<uuid>.<ext>` in `attachments.storage_key`, as before. Keys are generated by the API and checked
  against a fixed pattern before every request, so a key can never point elsewhere.
- Every download is checked against the SHA-256 recorded at upload (unchanged).
- Contract creation: the file is checked (type by content, size), written to the bucket, then the
  contract and its document row are saved in one transaction. If that fails, the object is
  deleted again. If the bucket cannot be written, no contract is created (HTTP 503,
  `STORAGE_ERROR`, plain message; the storage error is only logged by name on the server).
- An unreachable bucket is reported as `STORAGE_ERROR` (503), never as a missing file (404).

All document workflows use the same store: AMC contract documents and attachments, visit service
reports (Service Status), Service Sales report downloads, procurement and expense attachments.

Code: `src/shared/object-storage.ts` (S3ObjectStorage, used for Supabase and R2),
`src/config/storage-config.ts` (which store, validation), `src/shared/storage.ts` (local folder).

## File size

The application accepts files up to `ATTACHMENT_MAX_MB` = 12 MB. The Supabase Free plan's global
file size limit is 50 MB (it cannot be raised on Free). If you set a per-bucket "Restrict file
size" limit, keep it at **15 MB or more**, otherwise 12 MB files would be refused by Supabase
(the user would see a 503 "could not be saved" and no contract would be created).

## Choosing the store (API environment)

Exactly one may be configured; a partial set, or two stores, stops the API at start with a
message naming the missing variable (never a value).

| Variables set | Store |
|---|---|
| `SUPABASE_PROJECT_REF`, `SUPABASE_S3_REGION`, `SUPABASE_S3_BUCKET`, `SUPABASE_S3_ACCESS_KEY_ID`, `SUPABASE_S3_SECRET_ACCESS_KEY` | Private Supabase bucket |
| `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | Private Cloudflare R2 bucket |
| `ATTACHMENTS_DIR` | Local folder |
| none, development | `stslv-api/storage/attachments` (unchanged) |
| none, production | none: uploads and new contracts refused (unchanged) |

`SUPABASE_S3_ENDPOINT` is the **Endpoint exactly as shown on Storage → S3 Connection**. It is
technically optional (default `https://<project ref>.storage.supabase.co/storage/v1/s3`), but
**set it in production**: on 2026-11-04 the default host answered HTTP 400 "Project not
specified.", and the real bucket check passed only with the dashboard's Endpoint.

The project reference and the endpoint are separate settings. The reference stays required and
validated; it is not derived from, or replaced by, the endpoint. When a custom endpoint is set,
connections use the endpoint only. `npm run storage:check` reports, as a plain yes/no, whether the
endpoint's host contains the project reference, so a mismatch can be reviewed without either value
being printed.

Check a configuration end to end (uploads one probe file under `attachments/`, downloads it,
compares its SHA-256, deletes it and confirms it is gone; prints only the store kind and OK/FAIL,
never a secret or address). It needs no database settings. Against the real bucket, from
`stslv-api`, with credentials typed into masked prompts:

```
powershell -ExecutionPolicy Bypass -File scripts\check-supabase-storage.ps1
```

Real check passed 2026-11-04 (region ap-southeast-1, custom endpoint).

The Security page shows "Document storage: Supabase Storage (private)" when it is in use.

## Supabase setup (owner, in the Supabase dashboard)

Project `sgzvlmjkhhrwtuuqatve`, bucket `stslv-amc-documents` (already created, public off).

1. **Storage → Buckets → stslv-amc-documents → Edit bucket**: Public bucket **off**. Restrict file
   size: off, or 15 MB or more. Allowed MIME types: leave empty (the API already restricts types).
2. Add **no** storage policies for this bucket. The API uses S3 keys, which do not need policies,
   and with no policies the bucket cannot be reached with the project's public (anon) key.
3. **Project Settings → Storage → S3 Connection** (Storage → Settings in newer dashboards):
   - Make sure **Enable connection via S3 protocol** is on.
   - Note the **Region** shown there (for example `eu-central-1`): it is `SUPABASE_S3_REGION`.
   - Under **S3 Access Keys** → **New access key**, description `stslv-amc-api-render`.
     Supabase shows the **Access key ID** and the **Secret access key** once. Copy them straight
     into Render (next section); do not paste them into chat, email or any file.
   - These keys reach **every bucket in the project and bypass RLS**. Use this project only for
     STSLV AMC documents, and keep the keys on the server.

## Rotating or revoking the key

Create a new access key in Supabase, replace the two key variables in Render, let the service
restart, check that a contract document opens, then revoke the old key in Supabase.

## Free plan notes

- Free includes 1 GB of file storage and a monthly egress allowance (see the project's Usage page
  for the current figures); both are well above current needs.
- Supabase pauses Free projects after a period of inactivity. Storage requests then fail until the
  project is resumed from the dashboard; the API reports this as `STORAGE_ERROR`, and no contract
  is created without its document. Regular use keeps the project active.
- Storage has no versioning: a deleted object cannot be restored. The API never deletes a recorded
  document (replacements are new versions); it only deletes files whose save failed.

## Existing files

- Production never stored files (storage was off), so there is nothing to move. Confirm before
  deploying with a read-only `SELECT count(*) FROM attachments;` on Neon: it should be 0.
- Local development keeps using `stslv-api/storage/attachments`. Local files are not copied.
