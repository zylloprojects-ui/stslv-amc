# Session Security, Password Policy and Audit Log Protection (P0)

Prepared 2026-11-09 on `feature/stslv-p0-security`. Migrations **0108** and **0109** are applied only to
isolated test databases. Nothing has been applied to Neon.

## Server-side sessions (migration 0108)

Before: a sign-in token was valid for 8 hours whatever happened; signing out only forgot it in the browser.

Now each sign-in creates a row in `user_sessions` and the token carries its id (`sid`). Every request checks it.
A session ends when:

| Event | Reason recorded | Who |
|---|---|---|
| Sign out | `LOGOUT` | the user |
| "Sign out of all devices" (My Account) | `LOGOUT_ALL` | the user; every session including this one |
| "Sign out" on another device (My Account) | `REVOKED_BY_USER` | the user |
| Administrator signs out one session or all devices | `REVOKED_BY_ADMIN` | Super Admin / Admin with Users: Edit |
| Own password changed | `PASSWORD_CHANGED` | every **other** session; this device continues |
| Temporary password replaced | `PASSWORD_CHANGED` | every session (as before) |
| Temporary password issued by an administrator | `TEMPORARY_PASSWORD` | every session |
| Account deactivated | `DEACTIVATED` | every session |
| No use for `SESSION_IDLE_TIMEOUT_MINUTES` (default **30**, 5–1440) | `IDLE_TIMEOUT` | system |
| `JWT_EXPIRES_IN` reached (8 h) | — (expired) | system |

The existing `password_changed_at` check stays in force as well.

**Inactivity is real use, not requests.** The web application polls in the background (permissions every
minute, notifications), which must not keep an unattended screen signed in. Every request carries
`X-Idle-Seconds`: seconds since the last key press, click, touch, scroll or pointer movement in any tab of that
browser. The API records "now minus that" as the session's last activity (never moving it backwards) and ends
the session once the recorded activity is older than the limit. A client that sends no header (a script) counts
as active on each request. The header can only extend a session the holder already controls; it cannot revive
an ended one.

Responses: `401 SESSION_IDLE_TIMEOUT` ("You were signed out after 30 minutes of inactivity…"),
`401 SESSION_REVOKED`, or the generic `401 UNAUTHORIZED`. The sign-in page shows the first two messages.

**At release** every existing token (it has no `sid`) is refused once: everyone signs in again. No user,
password hash, role or permission changes. On a database without 0108 the API keeps the old behaviour.

### Endpoints

| Route | Access |
|---|---|
| `GET /api/auth/sessions` | signed-in user, own open sessions (current marked) |
| `DELETE /api/auth/sessions/:id` | own session only; another user's id answers 404 |
| `POST /api/auth/logout` | ends this session (was: record only) |
| `POST /api/auth/logout-all` | ends every own session |
| `GET /api/security/sessions` | administrators (Security Center): every open session |
| `GET /api/users/:id/sessions` | Users: View + administrator + may manage that user |
| `POST /api/users/:id/sessions/revoke` | Users: Edit + administrator + may manage that user |
| `DELETE /api/users/:id/sessions/:sid` | same |

"May manage" is the existing user-management rule: Admin cannot act on Super Admin or Admin accounts, nor on
anyone holding permissions Admin lacks. The six-role permission model is unchanged. Every revocation is in the
activity log (`auth.logout_all`, `auth.session_revoked`, `user.session_revoked`, `user.sessions_revoked`) and the
Login History filter includes them.

UI: My Account → **Active sessions** (list, sign out a device, sign out of all devices). Security Center →
**Active sessions** (all users; actions need Users: Edit) and the inactivity limit under Sign-in settings.

Ended sessions older than 90 days are removed when their user next signs in; the sign-in and sign-out events
stay in the activity log.

## Password policy (new passwords only)

Applies to sign-up, My Account, the forced change after a temporary password, and an administrator creating a
user. Existing passwords and hashes are untouched and keep working; nobody is forced to change.

1. At least **12** characters (was 10); at most 72 bytes (bcrypt limit, unchanged).
2. At least three of: lower-case, upper-case, digits, symbols/spaces.
3. At least 5 different characters.
4. Not a well-known weak word with digits/symbols added ("P@ssw0rd2026!", "Welcome@123", "Stslv@2026").
5. Not containing the person's email name or a 4+ letter part of their name (also with look-alike characters).

Server: `stslv-api/src/shared/password-policy.ts`. Web (same rules 1–4, instant feedback):
`stslv-web/src/lib/password.ts`. Temporary passwords generated by the system (16 random characters) are not
affected.

## Brute-force protection — review

In force, unchanged: per address 50 sign-in requests / 15 min; per address + email 5 failures / 15 min (cleared
by a success); sign-up 10 / 15 min; temporary passwords 10 per administrator / 15 min; bcrypt cost 12; the
same answer and timing for unknown emails. Added on the VPS: Nginx `limit_req` on `/api/auth/` (20/min per
address, burst 20) and fail2ban on repeated limit hits.

Findings, not changed (decisions for later):

- The limits are kept in the API process's memory: they reset on restart and are per process. Run **one** API
  process (the systemd unit does). A cluster would need a shared store.
- There is no per-account limit across addresses (a distributed guess against one account). Adding one lets a
  stranger lock a real user out; the current design deliberately avoids that. Revisit with MFA.
- No multi-factor authentication (out of P0 scope).

## Audit Log protection (migration 0109)

`activity_logs` becomes append-only: statement-level triggers refuse every UPDATE, DELETE and TRUNCATE
(error 42501, "The audit log is append-only"), including statements that match no row and cascades from other
tables. INSERT is untouched; no application path updates or deletes audit entries (checked at c6d8d19).

- **Owner limitation**: the role that owns the table can disable or drop the triggers. On Neon today the API
  connects as the owner. Closing that needs a separate runtime role with only SELECT and INSERT on the audit
  log — prepared as `deploy/hostinger/sql/runtime-role.sql`, not applied (approval and rehearsal needed).
- **Backups/restores**: unaffected. `pg_restore` loads rows with COPY before it creates the triggers;
  `--clean` drops the table rather than deleting rows.
- **Maintenance**: any future clean-up of audit rows becomes a deliberate, approved, owner-level step
  (disable triggers, act, re-enable, in one transaction). The untracked local script
  `src/scripts/demo-reset-cleanup.ts` in the main folder deletes audit rows and will be refused after 0109.
- Tests use `withAuditLogUnlocked()` (tests/helpers.ts, test schema only) for their own resets.
